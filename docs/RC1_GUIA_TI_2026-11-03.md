# RC1 — instalación y configuración para TI

Este documento prepara una instalación NUEVA. No autoriza cutover, Cloudflare, DNS, habilitación ciudadana ni cambio del despliegue de certificación. El código completo permanece en `release/formulario-produccion-2026-11`. Se distribuye el mismo JAR/imagen en desarrollo, integración y producción.

## Material y separación

| Material externo | Requisito / custodia |
|---|---|
| Imagen Formulario, Caddy, Inspector, ClamAV, MySQL, Nodo | Digests del manifiesto RC1; importar archivo de imágenes o usar registro autorizado. Nunca `latest` ni builds al arrancar producción. |
| PISEE | Runtime/binario validado, PKI de catálogo, credenciales aprobadas, MPGA y X.509 institucional existentes. No regenerar. Directorio de estado propio persistente. |
| Firma Formulario Ed25519 | Identidad productiva aprobada, privada PKCS8 0400, identificador y mapa de confianza pública con históricos. No reutilizar claves de laboratorios. |
| ACK SIGER | Mapa de claves PÚBLICAS institucionales, firmado/verificado por el procedimiento de intercambio. La privada permanece en Windows. |
| Credencial técnica PULL y operaciones | Secretos independientes por ambiente/función; entrega por custodia. No URL ni línea de comandos con valores. |
| ClaveÚnica | Client ID/Secret del ambiente, origen HTTPS institucional, `/redirect` y `/logout` aprobados, algoritmo permitido por el proveedor. Secretos en configtree, nunca React. |
| TLS | CA/clave/certificados de origen, SAN correcto para Caddy, app y MySQL, truststore Java que conserve las raíces gubernamentales. Fechas y cadena verificadas. |
| Respaldo | Clave GPG simétrica >=32 bytes en archivo privado separado del respaldo; custodios y copia fuera del anfitrión. No es una identidad SIGER. |

Las plantillas no son credenciales institucionales. `preparar.py --produccion` exige una identidad de firma externa; no genera una identidad de laboratorio como firma productiva. El inicializador conserva el uso previo sin ese flag exclusivamente para entornos nuevos de integración.

## Instalación cerrada reproducible

1. Revisar Ubuntu, Docker/Compose >=2.24.4, OpenSSL, Python 3.12+, GPG, disco/cuotas, reloj/NTP, rutas VPN/Docker, salida PISEE y resolución gubernamental. No reiniciar el anfitrión que mantiene certificación. Habilitación del daemon Docker y copia fuera del host son tareas TI de la máquina definitiva.
2. Importar imágenes RC1; comprobar SHA-256 del archivo e IDs del manifiesto. Clonar la rama/commit, verificar contratos y leer AGENTS. Mantener toda configuración y material personal fuera del checkout/build context. Revisar propietario uid 1000 para app/nodo y 999 para MySQL.
3. Crear un destino nuevo con el inicializador. Los argumentos siguientes son rutas/identificadores, nunca valores secretos:

```sh
sudo python3 scripts/ubuntu/preparar.py /srv/ddn-formulario-definitivo \
  --produccion --commit SHA_COMPLETO_RC1 --hostname HOST_AUTORIZADO.gob.cl \
  --project ddn-formulario-definitivo --port PUERTO_LOOPBACK_LIBRE \
  --receipt-private-key /custodia/receipt-key.pem \
  --receipt-trust /custodia/receipt-trust.json --receipt-key-id ID_APROBADO \
  --sin-claveunica --sin-confianza-ack
```

El arranque cerrado permite navegar adultos/NNA sin ClaveÚnica ni SIGER. No invocar sobre un destino existente. La CA interna nueva del inicializador sirve para enlaces privados; instalar en Caddy la cadena de origen aprobada antes del despliegue definitivo. No cambiar certificados PISEE. Los secretos iniciales nuevos no autorizan integración institucional.

4. Depositar runtime PISEE institucional en directorio privado y estado propio. Generar una config NUEVA con IP exacta; el original permanece intacto:

```sh
sudo python3 scripts/ubuntu/preparar-config-pisee.py \
  --source /custodia/nodo/runtime/config.json \
  --target /srv/ddn-formulario-definitivo/pisee/config-produccion.json \
  --backend IP_FIJA_BACKEND --node IP_FIJA_NODO --subnet SUBRED_PRIVADA_EXCLUSIVA
```

La red dedicada del overlay define IPs fijas. `ipPermitidas` contiene solo loopback y backend; sin comodines/CIDR. Revisar colisiones con TODAS las redes del host y VPN. Config RO, credenciales/certificados RO, estado RW; logs del nodo descartados porque INFO no garantiza ausencia de PII. No publicar 8084/8489. Salud usa socket local, no consultas periódicas a SRCeI.

5. Copiar **fuera de Git** `infra/ubuntu/production.env.example`, completar TODOS los digests/rutas, hostname, puerto libre y direcciones. El archivo definitivo no contiene una lista de identidades. Completar la configuración externa a partir del inicializador y del fragmento PISEE. Mantener recepción, PULL, retención/eliminación y envío registral cerrados hasta sus aprobaciones.
6. Verificar el manifiesto sin imprimirlo:

```sh
sudo python3 scripts/ubuntu/validar-rc1.py --env-file /custodia/production.env \
  --node-config /srv/ddn-formulario-definitivo/pisee/config-produccion.json \
  --properties /srv/ddn-formulario-definitivo/config/application.properties
```

7. Usar SOLO `infra/ubuntu/compose.yml` + `infra/ubuntu/compose.production.yml`. No usar overlays stub/lab en producción. No existe servicio build en el manifiesto resultante. Orden: MySQL saludable; perfil `migracion run --rm migrar`; luego `up -d --wait`. No ejecutar en el host actual sin un encargo posterior de instalación/cutover. Caddy publica únicamente loopback; cualquier transporte institucional/publicación se autoriza por separado.

## Matriz de configuración

| Ámbito | Configuración |
|---|---|
| DEV | `PISEE_ENVIRONMENT=DEV`, autorización DEV propia y lista acotada obligatoria. Sin certificados institucionales en CI. |
| Integración privada real | Proveedor `PRODUCTION`, gates institucionales y `PISEE_RESTRICTED_CAMPAIGN=true` con archivo privado montado explícitamente. Es la configuración del laboratorio actual. |
| Producción institucional | `PISEE_ENVIRONMENT=PRODUCTION`, `PISEE_RESTRICTED_CAMPAIGN=false`; sin `PISEE_ALLOWED_RUNS_PATH` ni volumen de campaña. RUN variables válidos, solo presentador de recorrido legítimo, finalidad y X.509 fijado/vigente obligatorios. |
| Apagar consultas | `PISEE_SRCEI_ENABLED=false` y reiniciar SOLO app. Continúan declaración manual, extranjero y NNA. No habilita envío de datos registrales ya persistidos. |
| Habilitar PISEE | enabled, production-authorized, legal-basis-approved, purpose `REGISTRO DE USUARIOS`, URL privada, ruta X509 y pin correctos. Nunca deshabilitar TLS/firma para resolver un error. |
| CU no disponible | `siger.claveunica.habilitada=false`, callback-approved=false: adultos declarados/NNA independientes. Si se habilita, las credenciales y URI obligatorias se validan al arrancar; no se ignora configuración inválida. |
| CU definitiva | Configtree `cu/siger.claveunica.client-id`, `...client-secret`; environment, public-origin, redirect-uri, logout-uri, id-token-algorithm y callback-approved externos. Origen productivo HTTPS .gob.cl sin puerto explícito. |
| SIGER cerrado | `publico.integracion.habilitada=false`, recepción/avisos/adultos/NNA/envío cerrados y CAS persistido false/false. Navegación y revisión siguen funcionando. |
| SIGER operativo futuro | Importar confianza pública ACK, credencial técnica propia y aprobaciones de avisos/custodia; habilitar config y después CAS con revisión esperada. Nunca activar recepción sin destino institucional verificado. |

El nombre exacto de los flags es el de `application.properties.example`; no sustituirlos por variables parecidas. No guardar propiedades duplicadas. La falta de material obligatorio para una integración habilitada falla cerrado; para preservar recorridos independientes, deshabilitar explícitamente esa integración mientras TI resuelve su configuración.

## Frontera ciudadana y privacidad

Solo el propio presentador puede disparar la consulta; tarjetas de terceros no consultan. RUN módulo 11, aviso/canal, sesión propietaria, CSRF, cuota por IP/sesión, reserva corta y lease, límite/concurrencia/timeout, deduplicación y rechazo tardío permanecen activos. No hay API libre de datos personales. La respuesta pública solo contiene campos faltantes/obligatorios y declaraciones del ciudadano, nunca atributos SRCeI. No habilitar DEBUG/TRACE, access logs con query/cookies/cuerpos, volcados HTTP ni tracing de solicitudes. Adulto declarado conserva autenticada=false.

El control visual se completa hasta revisión sin SIGER; el comprobante exige recepción autorizada y durable. No crear comprobantes de recepción ficticios para eludir esa barrera.

## ClaveÚnica y SIGER pendientes

El cliente implementa Authorization Code, state, nonce, validación JWT/issuer/audience/expiración, UserInfo, sesión fijada, descarte de tokens, logout oficial y CSRF. Tests usan proveedor controlado exclusivamente en pruebas, nunca una autenticación simulada en la instalación. El rechazo institucional actual y un callback privado no aprobado son habilitaciones externas; no requieren recompilar. No se acredita login productivo completo con un usuario real en RC1. La integración privada conserva el callback público ya aprobado y por eso no puede recibir el retorno en su propia sesión.

La VM definitiva SIGER debe proporcionar: hostname/SAN y CA/chain verificables, salida HTTPS al receptor, Bearer técnico propio, clave privada ACK Ed25519 Windows, identificador y clave pública de ACK, confianza en la firma pública Formulario y sus históricos, MySQL/custodia Windows NUEVOS, configuración externa y perfil del consumidor definitivo. No reutilizar U4/WSL/:25443. El Formulario expone el contrato PULL; no realiza POST a SIGER ni incorpora su hostname en el JAR. En Windows, endpoint/CA/credencial/almacén y claves se configuran externamente en el consumidor existente.

Para la próxima campaña: recurso inexistente con Bearer ausente/falso 401, válido 404; cola exclusiva, recepción cerrada antes de PULL; firma y hash canónico 1.0/1.1, adjuntos SHA-256, procedencias, COMMIT institucional antes de ACK firmado, reintento ambiguo, cero duplicados y persistencia tras reinicio. RC1 no ejecuta una nueva transferencia física ni califica la VM definitiva. El Formulario no puede demostrar el COMMIT de una VM todavía no instalada.

Correo/Graph no es un componente de esta instalación ni un efecto supuesto de recibir una comunicación. Si se exige notificación por correo para la habilitación institucional, queda pendiente su encargo/configuración y validación, junto con retención, capacidad, monitorización y seguridad finales.
