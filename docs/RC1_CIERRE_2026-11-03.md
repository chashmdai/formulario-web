## Cambios y garantías

`PoliticaPisee` exige campaña en DEV/CONTROLLED_TEST. En PRODUCTION, con gates, finalidad REGISTRO DE USUARIOS, certificado X.509 vigente y pin institucional, admite RUN variables válidos sin archivo de identidades. Una integración privada puede seleccionar explícitamente `PISEE_RESTRICTED_CAMPAIGN=true`; la instancia real actual conserva esta restricción y su única identidad. No se extiende la autorización de demostración a terceros. El preflight institucional rechaza campañas/stubs y manifiestos sin digests/red fija/healthchecks.

La ampliación de RUN no crea una API libre: la consulta sigue limitada al presentador, aviso/canal, sesión propietaria y CSRF, módulo 11, límites por IP/sesión, deduplicación, lease y rechazo de respuestas tardías, timeout y concurrencia. Las tarjetas de terceros no consultan. El XML conserva exactamente `entradaSRCel`, U+006C final. Los antecedentes SRCeI permanecen en backend y su procedencia/discrepancias; el ciudadano solo recibe faltantes y declaraciones, sin elevar adulto declarado a autenticación CU.

El overlay **de producción**, revisado sobre los componentes existentes, fija una subred exclusiva con backend/nodo estáticos; el generador crea una config nueva con solo la IP exacta del backend más loopback. No se cambian PKI, credenciales, MPGA ni X.509. El laboratorio usa ahora ese overlay con un añadido privado de campaña; no usa stub. No se publican puertos de MySQL/PISEE. Los logs del nodo no se conservan; la aplicación registra eventos enum sin cuerpos ni identificadores personales.

CU conserva botón y Authorization Code/state/nonce, token/UserInfo backend, validación JWT, sesión, logout y manejo de errores. Config externa habilita el cliente/callback sin recompilar. El laboratorio mantiene el retorno público aprobado: no acredita autenticación completa en la sesión privada. Adulto declarado, extranjero y NNA no dependen de esa habilitación. No se simula éxito del proveedor.

SIGER conserva 1.0/1.1, firmas históricas, procedencias, SHA-256/Ed25519, reservas, descargas, ACK, CAS, reintentos y conciliación. El receptor es PULL; cambiar hostname, CA, credencial o endpoint del consumidor Windows no modifica el JAR Formulario. No se generan claves productivas SIGER por defecto. La futura VM y su COMMIT antes del ACK deben comprobarse físicamente en otro encargo. Ninguna comunicación de campañas históricas fue reclamada.
